Phone to Production

The complete path a piece of work travels in my pipeline: from a chat message sent on a phone, through triage, an isolated build, independent multi-model review, and a mechanically enforced merge gate, back to a receipt in chat. Every security transition is deterministic code; no model can approve its own work.

The five rules the diagram keeps obeying

State on diskINBOX.md, BOARD.md, approvals/, attestations — any process can die mid-task and be replaced.
Deterministic boundariesApproval and merge gates are code and git hooks. A model can propose; it cannot cross.
Independent error profilesImplementer ≠ verifier; four models per review; an external gauge that owes the pipeline nothing.
Measured rostersEvery solo claim is adjudicated; seats are kept on precision, not reputation.
Silence is failureHeartbeat and progress have different owners; a receipt returns to the phone or something is wrong.

Stage notes

1 · Intake
The daemon holds no model — it filters, deduplicates, checks the sender, acknowledges. The first model in the path lives for exactly one message and can take exactly one action. Real development work is filed, never done on the spot.
Gate lane
Approvals are a whitelisted command writing a file atomically. Message content is never an approval signal, so quoted approvals, forwarded text, and persuasive prose are inert by construction.
2 · Campaign
Rows are points in a four-axis state space, so "done but needs a human" and "done but the reviewer objected" stay distinguishable. The commit lands before the slow steps — ordering is a reliability feature.
3 · Verification & merge
The branch faces an agent instructed to distrust it, then four models whose disagreements are preserved and attributed, then an optional external code-health gauge. The merge itself asks git, not the model, whether a fresh attestation exists.
